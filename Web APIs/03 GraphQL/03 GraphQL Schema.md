# GraphQL Schema

*   The first step when working with GraphQL is to define the schema
*   GraphQL cannot work without schema

## Role of Schema

*   The schema is used to:
    *   Define the shape of data
    *   Define queries
    *   Define mutations
    *   Define subscriptions

*   GraphQL uses the schema to:
    *   Validate queries and other operations
    *   Provide auto complete in playground
*   The schema uses type system to define:
    *   Field name
    *   Field type
    *   Nullability
*   The schema uses specialized language: Schema Definition Language
    *   Defines the objects, fields, type system, queries and more
*   The schema is sometimes auto-generated by GraphQL implementation.
    *   Based on the concrete language-specific objects.

## Object Type and Fields

*   The basic building blocks of the schema

*   Describe the entities (objects) and their properties in the system (fields).

*   Each field has a data type, indicating the type of data it can store

*   GraphQL specifications contain built-in Scalar types.

    *   Primitive types that hold a single value

        *   They are:
            * `Int`: A signed 32-bit integer (64, 5890, -17 etc)
            * `Float`: A signed double precision floating-point value (18.99 etc)
            * `String`: A string of characters UTF-8 encoded (“Hello world” etc)
            * `Boolean`: true or false
            * `ID`: A unique identifier, identical to String
            
        *   Most implementations add custom scalar types, like `date`.
    
            *   In these cases, you need to declare:
    
                ```apl
                scalar DateTime
                ```
    
    *   Complex types can be also defined
    
        ```apl
        type Author {
          authorId: Int!
          name: String!
        }
        ```

## Nullable Fields

Exclamation mark near the type of fields in the schema indicates that the field can't be null.

```apl
type Book {
  bookId: Int!
  name: String!
  pages: Int!
  price: Float!
  publishDate: DateTime
  author: Author
}
```

*   Required fields (marked with `!`): These fields **must** have a value.

    -   `bookId: Int!`
    -   `name: String!`
    -   `pages: Int!`
    -   `price: Float!`
    
*    Optional fields (no `!`): These fields **can be null or omitted**.

    -   `publishDate: DateTime`
    -   `author: Author`

## Enumerations

*   A special type of scalar
*   Limits the values a field can have to a predefined list
*   Great for making sure only valid values are selected.
*   Invalid values will be marked as error in GraphQL

```apl
type Book {
  bookId: Int!
  name: String!
  pages: Int!
  price: Float!
  publishDate: DateTime
  genre: BookGenre!
  author: Author
}

enum BookGenre {
  HORROR
  FANTASY
  DRAMA
  THRILLER
  NON_FICTION
}
```

## List

*   Objects can hold lists of the objects
*   Can be declared in the schema

```apl
type Book {
  bookId: Int!
  name: String!
  pages: Int!
  price: Float!
  publishDate: DateTime
  genre: BookGenre!
  author: Author
  reviews: [BookReview!]!
}

type BookReview {
  reviewId: Int!
  rating: Int!
  description: String!
  reviewDate: DateTime!
  user: String!
}
```

### Lists and Nulls

*   You need to pay special attention to list and nullable types
*   In our example: `reviews: [BookReview!]!`
    *   There are two exclamation marks
        *   The inner `!` means "the list cannot contain `null` items"
        *   The outer `!` means "the attribute `reviews` cannot be `null`"

## Interfaces

Similar to modern development languages, GraphQL allows defining interfaces

*   An abstract type with set of fields
*   In order to implement interfaces, a type must include this set
*   Allows working with multiple types using a single interface.

```apl
interface IReadingMaterials {
  name: String!
  genre: BookGenre!
}

type Book implements IReadingMaterials {
  bookId: Int!
  name: String!
  pages: Int!
  price: Float!
  publishDate: DateTime
  genre: BookGenre!
  author: Author
  reviews: [BookReview!]
}

type Magazine implements IReadingMaterials {
  magId: ID!
  name: String!
  genre: BookGenre!
  issueNo: Int!
}
```

So now, you can create a query for `IReadingMaterials` that will fetch both books and magazines data

```apl
query {
  IReadingMaterials {
    name
    genre
  }
}
```

## Unions

*   Similar to interfaces
    *   allow querying multiple objects types in a single query.
*   In contrast to interface, object types do not have common fields
*   Query can specify which field to retrieve from each object type

```apl
union Things = Book | Magazine
```

Now you can query:

```apl
query {
  Things {
    __typename
    ... on Book {
      name
      publishDate
      reviews{
        rating
      }
    }
    
    ... on Magazine {
      name
      issueNo
    }
  }
}
```

## Input type

An input type defines the shape of data that clients can send to the server — usually as arguments for mutations (and sometimes for queries).

*   While **object types** describe the shape of data you *receive* from the server, **input types** describe the shape of data you *send* **to** the server.

## Schema directive

a directive is a built-in mechanism for attaching extra behavior or metadata to part of a schema or query.

*   Formally, a directive is a **named instruction** that tells the GraphQL execution or tooling layers to do *something special* with the element it decorates

THe Schema-time directives extend or customize how parts of the schema behave for *all* queries.

```apl
directive @auth(role: Role!) on FIELD_DEFINITION

type Query {
  users: [User!]! @auth(role: ADMIN)
}
```

*   `directive @auth(role: Role!) on FIELD_DEFINITION`

    *   defines a new directive named **`@auth`** that can appear on **field definitions** in the schema.

    *   It takes one argument, `role`, whose type is `Role!` (a required enum or scalar).

    *   `FIELD_DEFINITION` means that this directive is for field definitions, some other values are:

        ```
        SCHEMA | OBJECT | FIELD_DEFINITION | ARGUMENT_DEFINITION |
        INTERFACE | UNION | ENUM | ENUM_VALUE |
        INPUT_OBJECT | INPUT_FIELD_DEFINITION
        ```

*   `users: [User!]! @auth(role: ADMIN)`

    *   attaches that directive to the `users` field.

    *   the runtime calls the auth directive’s function first, that is like a REST API middleware:

        ```js
        function authDirective(role, nextResolver) {
          if (currentUser.role !== role) {
            throw new Error("Forbidden")
          }
          return nextResolver()
        }
        ```

##  On On the Order of Definitions in GraphQL Schemas

In GraphQL, the order of type definitions has no effect on execution.
 The schema language is declarative, not procedural, which means the GraphQL engine reads and validates the entire schema before resolving any references.
 You can freely define a type or interface before or after it’s used — both will work exactly the same.

That said, adopting a consistent logical order makes schemas easier for humans to read and maintain.
 A common and clear structure is:

1. **Scalars and Enums**  
   
   *   Define any custom scalars (e.g. `DateTime`) and  enums used throughout the schema.
   
2. **Input Types**  
   
   *   These define the shape of arguments passed into queries and mutations.  
   *   They’re similar to object types, but used *for input* rather than output.  
   *   It makes sense to place them early (right after scalars/enums) so they’re available before mutations or object types refer to them.
   
3. **Interfaces and Unions**  
   
   *   Define shared or polymorphic types used by objects.
   
4. **Object Types**  
   
   *   Your domain models, like `User`, `Post`, `Comment`, etc.
   
5. **Root Types**  
   
   *   `Query`, `Mutation`, and `Subscription`.
   
6. **Schema Definition** *(optional, if needed)*  
   
   *   Explicitly bind root types:
   
       ```apl
       schema {
         query: Query
         mutation: Mutation
       }
       ```
