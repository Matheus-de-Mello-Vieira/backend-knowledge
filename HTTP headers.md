# HTTP headers

## Caching Headers

Caching is about storing responses to reuse them for later, to reduce load, latency, and bandwidth. Caching headers tell clients and intermediaries how and when to cache a response.

### Cache control

* Comma separated list with multiple directives:
  * `cache-control: directive-1, directive-2`

  * `cache-control: private, max-age=60`

* Some directives have an optional argument
  * ie.: `cache-control: public, max-age=6400`
* There is request and response cache control headers
  * response:
    * who can can cache the response?
    * for how long?
    * Under what conditions?

  * request
    * override the caching behavior
    * protect sensitive data from caching

* directives:
  * `max-age=N`:  request and response

    * request:  Indicates that the client allows a cached response that was generated by the origin server no more than N seconds ago.
      * `Cache-Control: max-age=0` can act as a workaround for `no-cache`, especially since some older (HTTP/1.0) cache implementations don't support `no-cache`.
    * response: indicates that the response remains fresh until N seconds after the response is generated.

  * `max-stale=N`: (Request only) Indicates that the client is willing to accept a cached response that has expired, as long as it is no more than N seconds stale.

    * If no N value is specified, the client will accept a stale response of any age.
    * This can be useful if the origin server is down or slow, and the client prefers older content over no content.
    * Note: Major browsers do **not** support sending requests with `max-stale`.

  * `min-fresh=N`: (Request only) indicates that the client allows a stored response only if it will remain fresh for at least *N* more seconds.
    * This can be used when a user requires not just fresh data, but also data that won’t expire for a specific time period (for example, to avoid interruptions during long operations).
    * Note: Major browsers do **not** support sending requests with `min-fresh`.
  * `no-store`: don't store caches
  * `no-cache` store cache, but always revalidate before each use
  * `private`: cache only on user device
    * private data is meant for a single user
  * `public`: resource may be cached by any place
    * it is the default
* pratices
  * Take advantage of caching especially for high volume API
  * Consider `no-store` and `private` for sentivedata
  * Provide the validation tag (`ETag`) especially for large responses
  * Carefully decide on the optimal `max-age`
  * If your data change in a unpredictable way, use `no-cache` 


### Expires

```txt
Expires: Wed, 21 Oct 2015 07:28:00 GMT
```

Contains the date/time after which the response is considered expired in the context of HTTP caching.
* The value `0` is used to represent a date in the past, indicating the resource has already expired.
* The format is `<day-name>, <day> <month> <year> <hour>:<minute>:<second> GMT`

### Last-modified

```
Last-Modified: Wed, 21 Oct 2015 07:28:00 GMT
```

Contains a date and time when the origin server believes the resource was last modified.
* On the following requests, the clients sends this value on `If-Modified-Since` or `If-Unmodified-Since`
  * It is less accurate than an ETag for determining file contents, but can be used as a fallback mechanism if ETags are unavailable.
* The format is `Last-Modified: <day-name>, <day> <month> <year> <hour>:<minute>:<second> GMT`


### Etag

```txt
ETag: W/"<etag_value>"
ETag: "<etag_value>"
```

* Unique identifier associated with a response
* Enable clients to send Conditional Request Headers with that value in future requests.
* It is strong by default, but it can be prefixed with `W/` making it weak.
  * strong ETags: two files are equal only if they are byte-for-byte identical
    * strong ETags only matches with strong ETags
    * more costly to generate, but more reliable for precise comparison.
    * In practice, most APIs only use strong ETags for write/concurrency control.
  * weak ETags: two resources are considered equal if their content is equivalent, even if not identical at the byte level.
    * the definition of 'content equivalence' can vary between different implementations.
    * cheaper to generate, but less precise—useful for cases where small differences are not significant.
* `ETag` can be obtained strategically to streamline the process
  * **Most common:** The server queries at least the *metadata* of the resource to get its ETag, even if it doesn’t load the entire object body.
  * **Efficient storage:** Some servers store ETag values in a fast-access place (like a database column or cache) alongside the resource, so they can check ETags without reading the whole file or object.
  * **Calculated on demand:** Sometimes the ETag is generated dynamically (e.g., a hash of the content), in which case the server needs to read the object data to generate it.

### Vary

```txt
Vary: *
Vary: <header-name>, …, <header-nameN>
```

* response only
* a list of strings
  * it also can be a `*`, indicating that factors other than request headers influenced the generation of this response.
    * Implies that the response is uncacheable.
* on cache, indicates the client to to cache separately responses with different values on the headers listed in `vary`.
  * Vary specifies which request headers make responses "different" from a caching perspective.
  * the `Vary` header indicates which request header fields define distinct variants of the response.
    * If the value(s) of any header listed in `Vary` differ between requests, each response is considered a separate variant.
  * it is used mainly with content negotiation headers
  * for example, `Vary: Accept-Language`, will indicate the client to cache requests with `Accept-Language: en` separately from those with `Accept-Language: ja`.

## Conditional Request Headers

Conditional Request Headers are used to make requests that are processed only if certain conditions are met on the server, like the state of a resource.

### If-Match

"Execute only if any of these ETags match."

The server obtains the current ETag of the resource by its own means, and if it matches any of the strings in `If-Match`, it responds with:

* It is a list of quoted strings, separated by `, ` (a comma and a space).
  * Each string can be prefixed by `W/`, which denotes a weak ETag, but it in pratice make the prefixed string never match with anything.
  * It can also be a single `*`, meaning "any ETag," which in practice means the request will only succeed if the resource exists.
* The server obtains the current ETag of the resource by its own means:
  * If it matches any of the strings in `If-Match`, it responds normally
  * Otherwise it responses with `412 Precondition Failed`
* Common use cases
  * For `PUT` or `DELETE`: **Concurrency Control** — to avoid accidentally make changes based on outdated data.
    * For **PUT**, is possible to use `*` when you want to make sure you’re only updating and never creating by mistake, and you don't care about the current data being overwritten.

  *  For `GET` (rare): **Range requests consistency**— methods, that uses `Range` header(= get only a part of file), it ensures that all ranges comes from the same resource.
    * although this is possible, it is better to use `If-Range`, which was specifically designed for this purpose.


### If-None-Match

"Execute only if none of these ETags match."

```txt
If-None-Match: "bfc13a64729c4290ef5b2c2730249c88ca92d82d"
If-None-Match: W/"67ab43", "54ed21", "7892dd"
If-None-Match: *
```

* It is a list of quoted strings, separated by `, ` (a comma and a space).
  * Each string can be prefixed by `W/`, which denotes a weak ETag, but this has no practical effect on `If-None-Match`.
  * It can also be a single `*`, meaning "any ETag," which in practice means the request will only succeed if the resource does not exist.
    * This is only useful with `PUT`, where you can avoid overwriting any existing data.
* The server obtains the current ETag of the resource by its own means:
  * If it matches any of the strings in `If-None-Match`, it responds:
    * with `304 Not Modified` for `GET` or `HEAD` requests,
    * with `412 Precondition Failed` for any other method.
  * Otherwise, it responds normally, that includes the response headers `Cache-Control`, `Content-Location`, `Date`, `ETag`, `Expires`, and `Vary`.
* Its purpose is:
  * For `GET` or `HEAD`: **Efficiency** — to check if a cached resource is still valid.
  * For `PUT` (with `If-None-Match: *`): **Safety** — only create the resource if it does not exist.

## CORS

CORS (Cross-Origin Resource Sharing) is a security mechanism implemented by web browsers to control how web pages can make requests to resources on a different origin (domain, protocol, or port) than their.

A **same-origin** request happens when a web page and the resource it accesses share the **same domain, protocol, and port** — for example, a page from `https://example.com` requesting data from `https://example.com/api/data`.

A **cross-origin** request occurs when any of those three parts (domain, protocol, or port) differ. For example:

-   `https://example.com` → `https://api.example.com/data` (**different subdomain**)
-   `https://example.com` → `http://example.com/api/data` (**different protocol**)
-   `https://example.com` → `https://another-site.com/data` (**different domain**)

Browsers treat these cases differently for security reasons, using a mechanism called **CORS (Cross-Origin Resource Sharing)** to control which cross-origin requests are allowed.

Modern browsers isolate websites by “origin” (domain + protocol + port).

*   This is part of the **Same-Origin Policy (SOP)** — one of the web’s core security models.

CORS is a *controlled relaxation* of that policy, allowing *safe and intentional* sharing of data across origins.

### How CORS Works

When a web page makes a cross-origin request (like using `fetch()` or `XMLHttpRequest`), the browser first checks the server’s response headers to see if the resource allows such requests.

| **Header**                         | **Description**                                              | **Example Value**                                            |
| ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `Access-Control-Allow-Origin`      | Specifies which origin(s) are allowed to access the resource. | `Access-Control-Allow-Origin: https://example.com``Access-Control-Allow-Origin: *` |
| `Access-Control-Allow-Methods`     | Lists the HTTP methods allowed when accessing the resource.  | `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS` |
| `Access-Control-Allow-Headers`     | Specifies which custom headers can be sent by the browser.   | `Access-Control-Allow-Headers: Content-Type, Authorization, X-Requested-With` |
| `Access-Control-Allow-Credentials` | Indicates whether cookies or other credentials can be included in requests. | `Access-Control-Allow-Credentials: true`                     |
| `Access-Control-Expose-Headers`    | Lists which response headers can be accessed by JavaScript in the browser. | `Access-Control-Expose-Headers: Content-Length, X-Custom-Header` |

The **browser** uses the CORS headers to **decide whether it’s safe and allowed** to share the response with the page’s JavaScript code.

1)   The server responds with a subset of the aforementioned headers

2)   The browser checks if the requests fits on those response headers.

     *   In case of `Access-Control-Allow-Origin`, the request header `Origin` must fit on it.

3)   If they match, the browser **lets the page access the response** (e.g., `fetch()` or `XMLHttpRequest` can read it).

4)   If they **don’t match**, the browser **blocks the response**, even though the request technically reached the server.

     >   The data is fetched but **not made available** to JavaScript for security reasons.

#### Simple vs. Preflight Requests

*   **Simple Requests**
     If the request is “simple” (like `GET` or `POST` with standard headers), the browser just sends it directly, but still checks the response for CORS headers.

*   **Preflight Requests**
     If the request uses custom headers, non-simple methods (`PUT`, `DELETE`, etc.), or credentials, the browser sends an **OPTIONS** request first.
     This is called a **preflight request**, asking:

	>   “Hey server, can I send this request?”

	The server must respond with headers that approve it; otherwise, the browser cancels the actual request.

#### Access-Control-Allow-Credentials

>   “It’s okay to include and expose **credentials** (like cookies, Authorization headers, or TLS client certificates) in cross-origin requests.”

If the page wants to send cookies or authentication headers, the browser only includes them if:

-   The request sets `fetch(..., { credentials: 'include' })`, **and**
-   The server responds with `Access-Control-Allow-Credentials: true`, **and**
-   `Access-Control-Allow-Origin` is **not `\*`** (it must be a specific origin).

Otherwise, cookies are stripped for security.

## Why CORS Exists

CORS (Cross-Origin Resource Sharing) exists to protect users from malicious websites that try to read or manipulate private data from other sites where the user is logged in.

### Generic scenario

Let’s imagine you’re logged into:

```url
https://mybank.com
```

and your browser stores your session cookie for that site.

Now, you visit a **malicious website**:

```url
https://evil.com
```

If browsers didn’t enforce the same-origin policy (or CORS), this evil site could do:

```javascript
fetch('https://mybank.com/account', {
  credentials: 'include'
})
  .then(response => response.text())
  .then(data => sendToHackerServer(data));
```

Your browser would **automatically include your cookies** (since you’re logged in), and the hacker could read your **account info** — even though you never interacted with your bank site directly.

### Attacks CORS Helps Prevent

#### 1. **Cross-Site Request Forgery (CSRF)**

“Make the user’s browser do something on another site.”

-   **Definition:** An attacker tricks a user’s browser into making authenticated requests to another site where the user is logged in.
-   **Goal:** Perform actions (like transferring money or changing passwords) without the user’s consent.
-   **Limitation:** The attacker *cannot see the response* — they just cause actions to happen.
-   **CORS relevance:** CORS doesn’t stop the *request*, but it stops the attacker from *reading* the response.
-   **Example**: Transfer money, change password

#### 2. **Cross-Site Data Theft / Cross-Site Scripted Request**

 “Make the user’s browser *read something* from another site.”

-   **Definition:** An attacker tries to **read private data** from another site via a cross-origin request.
-   **Goal:** Extract sensitive information (e.g., account balances, emails).
-   **CORS relevance:** This is **exactly what CORS prevents** — browsers block access to the response unless the target site explicitly allows it with `Access-Control-Allow-Origin`.
-   **Example**: Read account balance, download user data

## Common Misconceptions

*   CORS is **not a server-side security feature** — it’s enforced by browsers only.
*   Setting `Access-Control-Allow-Origin: *` doesn’t make your API secure — it just removes CORS restrictions for browsers.
*   CORS errors do **not** mean the server is broken; they mean the **browser** is blocking access.
